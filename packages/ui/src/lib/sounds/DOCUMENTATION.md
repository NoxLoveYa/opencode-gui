# Sounds

Short sounds for typing, sending and events from the agent, played on this device only.

## Ownership

`lib/sounds` owns the audio engine, the built-in voices, the sound settings store, custom sound files, the rules that decide whether a sound plays, and the facade the rest of the app calls (`signals.ts`). `useSoundSystem` is mounted once per window by `SyncRuntimeEffects`, so every runtime shell (web, desktop, mini chat, VS Code, mobile) has it. The Sounds settings page lives in `components/sections/openchamber/sounds/`; the typing hook lives in `components/chat/composer/editor/soundFeedback.ts`. Agent events are detected here and in the sync layer's announce points (`sync/DOCUMENTATION.md`, *Sound hook points*). The rest are detected where the user's action or the store that holds the fact lives (dictation in `hooks/useDictation.ts`, copy in `lib/clipboard.ts`, commits in `lib/gitApiHttp.ts`) or in `workspaceSources.ts`. A row stays off the page until `wired` is set in `events.ts`.

- `events.ts` is the catalogue: every event id with its tab, default settings, throttle, runtime availability and whether the page shows it. The settings schema covers all of them, so stored settings never need a migration when another event is wired.
- `settings.ts` holds the types, defaults and the zod schemas that read stored settings. `soundSettingsStore.ts` is the persisted store (`openchamber.sounds.v1`).
- `gate.ts` is the pure decision whether an event may play now. `throttle.ts` (minimum gap per event, same-key coalescing) and `claims.ts` (one window per origin plays a remote event) keep state and run after it, inside `signals.ts`.
- `voices.ts` describes the built-in voices as data and renders them with Web Audio. `engine.ts` owns the `AudioContext`. `customSounds.ts` stores user files in IndexedDB.
- `turnEnd.ts` turns the live busy-to-idle status transitions plus the sync layer's outcome hints into at most one sound per turn: session finished, subagent finished or error. `reminders.ts` plays the permission and question sounds and repeats a reminder while the request still waits. Both are driven by `useSoundSystem` and the sync layer, and both call `signals.ts` like any other source.
- `agentActivity.ts` turns the live start of a turn into the start sounds (a subagent at once, a main session with its first output) and classifies a tool call's state change as a tick or a file edit. `connection.ts` turns `useConfigStore.connectionPhase` into the lost and restored sounds. `workspaceEvents.ts` holds the pure detector for background command ends and the pull request watcher; `workspaceSources.ts` subscribes them, with the git commit and push buses, the tracked records the server sent and the control stream, once per window (`startWorkspaceSounds`). A terminal's end is announced from three live places that share one claim: the `exit` handlers of `TerminalView` and of the project action runner, and the server's session-change notice that names the exited session (`workspaceSources.ts`). All call `soundSignals.terminalFinished(sessionId, exitSequence)`. The project action runner's Stop calls `terminalStopped` and, when the process survives it, `terminalStopFailed`.
- `nativeNotifications.ts` decides which native notification kinds the desktop shell may show without the OS sound, because this device plays an OpenChamber sound for them. `useSoundSystem` reports the result to the shell.

## Invariants

- A sound comes only from a live event or this window's own user action. Bootstrap, snapshots, resyncs and persisted state never play one.
- Nothing in `lib/sounds` creates an `AudioContext` before some sound is wanted, and nothing runs a timer while no sound is playing. A context that has been idle for 4 seconds is suspended, one that was only unlocked by a gesture included. Only the Electron shell, which starts audio without a gesture, creates its context at that point (`probe`); a browser waits for a gesture or a sound.
- The gesture listeners that unlock audio exist only while sounds are on, not muted, a shown event is switched on and the engine is locked.
- A context that cannot be resumed after an idle suspend makes the engine `locked` again, which brings the listeners and the page hint back; a sound is never dropped silently for good.
- A custom file is read and decoded once per file id, a failure included, and a removed or replaced file is forgotten. A voice that fails after its slot is taken gives the slot back.
- Typing and erasing share three voices, sending has two of its own, everything else six.
- Typing feedback never writes React state or a store.
- A failed custom file read plays the event's default voice. A failed store leaves the previous source in place, and an event never points at a file that was not stored.
- Stored settings are read field by field. One damaged value takes its default and never resets the rest. A removed key (another window cleared it) keeps this window's settings and never rehydrates to the defaults, since the sweep would then delete files events still use.
- Sounds never take part in reading or dictation audio. Sounds have their own context, and while dictation records, every sound but the dictation ones is held back.
- A turn plays at most one end sound in a window, and an end sound, a request sound or a reminder plays in at most one window of an origin (one claim per key). A turn is named by the server's stamp for its end, so two quick turns of one session play once each. Stopping a turn (an error that reads as a stop included), a subagent failing and a request the server answers by itself play nothing. Failures of several sessions within two seconds play one error sound.
- "Only in background" is judged in the window the user looks at: that window takes the claim of an event it holds back, without a sound, so a hidden window of the same origin never plays it.
- A reminder runs only while its request still waits (a complete directory store decides for permissions and forms, the blocking index for the rest) and the user is not looking at its session. It never runs a timer while no request waits. Quiet hours and similar holds postpone it without using up a repeat; "in background" in the window the user looks at sends it silently and uses the repeat.
- A start sound, a tick and a workspace sound come only from a live event: a status the host reported or a part snapshot is no start or tick, and a start the server replays after a reconnect plays nothing. Every tracked record of a pull request the window gets (restored from storage, the answer to what it follows, a pushed change) sets the baseline, and only a pushed change the server marks `continuous` is compared with it. A terminal ends only through the live `exit` event of its stream or the server's exit notice for its session; the terminal store's lifecycle (a failed stream, a list read after a restart, a snapshot, a stop) never announces one.
- The sync layer's per-event cost for sounds is one `Set` size read for a delta, and for a tool transition one settings read (`toolSoundsWanted`). Both return before touching the session lists while the sounds are off.
- A tick or a file edit sound is made only for the session on screen in the window the user looks at, and at most about eight ticks and four edit sounds a second.
- The engine reports when a sound has left the speakers: its scheduled end after any resume, plus the output and base latency and 150 ms (a custom file counts by its stored length), or 0 when it was not played. The capture throws away the audio up to that time. While the microphone records, every sound but the two dictation ones is held back, and each dictation holds on its own: it releases only the hold it took.
- A connection that dropped makes no sound unless it stays down for 4 seconds in a visible window that was not shown again less than 10 seconds before the drop, and "restored" plays only after a "lost" the settings allowed. An instance switch clears both.
- The OS notification sound is muted only for kinds this window reports as covered while its engine is unlocked, for notifications of the instance the window shows. The shell forgets a report when the window closes or commits another page.

## Decisions

### Why sounds have their own AudioContext and not the speech one

Android reading audio focus suspends the reading provider's context on a transient loss, and readings stop and replace their playback. Sharing it would mute sounds during a reading pause and let sound scheduling interfere with reading cleanup. A reading in progress only holds back the frequent, low-value sounds (`duringReading` in `events.ts`).

### Why sound settings live in their own store and not in the settings registry

The registry describes what crosses the wire and how a server document seeds the client. Sound settings never had a server copy, and the bytes of a custom file cannot live in a settings document. One module keeps parsing, defaults and file references together. The cost is that they are not in `LOCAL_DEVICE_KEYS`, whose test only covers `useUIStore`. Settings are per origin, like every other device setting: a desktop window on a remote instance has its own.

### Why custom files are in IndexedDB and not a data URL in localStorage

localStorage is a shared 5 MB budget read synchronously, base64 grows a file by a third, and in VS Code every write is copied into every webview as a `StorageEvent`. IndexedDB fires none. For the same reason a slider writes its value once on release, not per step. Files are limited to 1 MiB each, 8 MiB in total and 10 seconds. The length is checked right after the decode and before the samples are scanned for the peak, since a long low-bitrate file fits the byte limit and decodes to millions of samples. The file a pick replaces does not count against the total, because it is deleted right after. The sounds page sweeps records no event points at, leaving the ones created in the last minute to a window that may be about to point at them; it also sweeps only against the settings of this window, which is why a removed storage key must not rehydrate to the defaults. A connection the browser closes or that another tab upgrades is dropped, and the next call opens a new one.

### Why audio unlocks on a gesture and early sounds are dropped

Browsers keep a context silent until a user gesture. While some sound could play (sounds on, not muted, a shown and available event switched on) and the context is locked, `useSoundSystem` listens for the first click, key press or touch and unlocks; when every sound is off the page installs no listener at all. A sound requested before that is dropped: one that arrives late is worse than none. Desktop shells that allow audio without a gesture start running by themselves, and the engine sees that and plays. The status stays `locked` until a context exists, and the context is made by the first sound or gesture, so in Electron the window would report no covered notification kinds until then and its first native notification would ring the OS sound next to ours. `useSoundSystem` therefore calls `probe` in the Electron shell while sounds are wanted: it creates the context, reports `ready` when the context runs by itself and lets the idle suspend put it to sleep. A browser would log an autoplay warning for a context made before a gesture, so it keeps waiting for the gesture. `unlock()` arms the idle suspend itself, because a context woken only by a gesture has no voice whose end would arm it. iOS WebKit may fail to resume a context outside a gesture, so the idle suspend is off there until a device run shows it is safe. Anywhere else, a resume after an idle suspend can still be refused (a browser that revoked the gesture grant); the engine then goes back to `locked` and notifies subscribers, so the listeners return and the page shows the hint instead of dropping sounds forever.

### Why the engine sets an ambient audio session

Where `navigator.audioSession` exists (Safari 16.4 and later, iOS included), the engine sets its type to `ambient` before it creates the context. The default plays Web Audio as media: it pauses the user's music and ignores the silent switch, which a keystroke click must not do.

### Why a custom file's load is cached with its failure

Each play of a custom event used to read IndexedDB and decode again when the file was missing or undecodable, one transaction per keystroke. The engine now keeps one promise per file id, failures included, so concurrent plays share one decode and a missing file costs one read. The cache is bounded (12 files) and `customSounds` tells the engine when a file is removed or swept, so a replaced file drops its decoded buffer. A transient storage failure is therefore remembered until the file is replaced or the window reloads; that is accepted because the alternative is the retry per keystroke.

### Why sending has its own voice slots

Typing and erasing fill the three input voices during a burst, and a send that arrives right after would be dropped. The send sound is rare and the one a user waits for, so it gets two slots that typing cannot take.

### Why the stored settings are read with zod `catch` fallbacks

Each field carries its own default, so a damaged field, a damaged event entry or an event id added since the data was stored never costs the rest. Unknown event ids are dropped. The schema never throws, which keeps a bad storage value from reaching the UI.

### Why claims prefer the window the user looks at

An event that every window hears (an agent finished) plays once per origin: the first window to claim its key plays it, under a Web Lock. "Only in background" must be judged where the user is, so an unattended window waits 150 ms before claiming and the attended one almost always wins. The attended window of an event set to "in background" does not play, but it still takes the claim at once: without that, the hidden window (another tab, the desktop mini chat, a second VS Code webview) would win the claim 150 ms later and play the sound the user asked to hear only while away. The same holds for each reminder repeat. Local events (typing, sending) never claim.

### Why a turn is named by the server's end stamp

A claim keyed by session alone made the sound of a second quick turn of that session play nowhere while the first claim lived. OpenCode's `session.execution.succeeded`, `.interrupted` and `.failed` carry the server's time, which the client reads as `time.idle` of the `session.patched` it translates them to. Every window receives the same value, so `turn-end:<sessionId>:<stamp>` names one turn in every window and may keep a long claim, while the next turn has another stamp. A bare `session.idle` carries no stamp; such a turn keeps the session-only key with a 10 second claim. The stamp is read when the turn resolves, and it is dropped after 5 seconds like an outcome hint.

### Why a background command does not hold the end sound back

The status index keeps a session's turn open while it waits on a background command or a watched pull request, because the server wakes the session when they finish. For the sound that was wrong in the common case: an agent that starts a dev server and ends its turn never chimed, since the server keeps running. Only a running subagent holds the sound back now; its result hands the turn back at once, so the real end is a later edge.

### Why a failure with no edge starts the same wait

A failure of a session this window never saw run (the busy edge comes in the same batch, published after the events are handled) used to play at once and leave its hint behind, which then tainted the next turn within five seconds. Now it starts the 400 ms wait itself. A busy edge that the same batch publishes takes the wait over, the turn resolves once, and resolving consumes the hint.

### Why a turn end is a status edge, a short wait and an outcome hint

The status transition hook (`subscribeSessionStatusTransitions`) fires only for live `session.status`, `session.idle` and `session.error` events, so history loads and snapshots cannot play a sound. A busy to idle edge starts a 400 ms wait because a background subagent or command handing its result back runs the session again at once, and that is one turn, not two. The wait also absorbs the second idle OpenCode 2.x sends for one turn, which is no edge, since the session is no longer running. What the edge means (done, subagent done, error, stopped by the user) comes from the hint the sync layer records for each `session.idle` and `session.error`, because the status event alone does not say. The hint can arrive before or after the edge, depending on how events were batched, so both are kept and read together when the wait ends. The server's own notification pipeline is not used: it is gated by the notification toggles and debounced per channel, and sounds must work with notifications off.

A session counts as running for the edge if this tracker saw it run or the published status index still lists it, which is how a turn that was already running when the page loaded plays its one sound at the end. A subagent's failure plays nothing, since its parent receives it as a tool result. A turn whose session still has a running subagent plays nothing yet; the session's real end is a later edge. Without a hint, the tracker asks the sync layer whether the session is a subagent, and a `/btw` fork is not one.

### Why requests that wait for the user use the blocking index and a seen marker

A reminder asks whether the request still waits when it comes due, so a request answered anywhere ends its reminders without a subscription. A complete directory store answers for the permissions and forms it holds, because its reply and reconnect paths clear what the blocking index keeps after a lost event; the index answers for pages, which only it holds, and when no complete store exists. The sync layer installs both that check (`setReminderPendingChecker`) and the "is this session on screen" check (`setReminderViewChecker`), because it owns the stores and sits above this module. A waiting page is a request of its own kind: its id is a tool call id that two sessions can share, so every claim (sound, reminder, seen marker) names it `page:<sessionId>:<pageId>`. Opening the session ends the reminder, and the window writes a `reminder-seen` claim, so a hidden window of the same origin does not remind about a request the user already looked at. The permission and question sounds are announced from `notifyPermissionAsked`, `notifyFormCreated` and `notifyWaitingPage`, the points that already know the request is meant for the user: a permission held back for an automatic answer reaches them only when the server leaves it for the user.

### Why a reconnect allows each remote event once for three seconds

After a reconnect the server replays a bounded suffix of the events the window missed, with no flag that marks them. A gap that ended several turns would otherwise play a burst. For three seconds after a non-first reconnect (or a transport switch) each event that every window hears plays at most once. The start sounds are the exception: a start replayed after a gap is history, so `agentStarted` and `subagentStarted` drop out entirely in that window and do not use up the slot of a start that is live. Events the user causes, like typing, are not held back. A kind's slot is used up only when its sound is about to play, after the throttle and the claim, so a sound another window took does not cost this window's slot. A transport switch followed by a reconnect extends the one window and keeps the slots already used, instead of opening a second window that would allow a second burst.

### Why the OS notification sound is muted from a report by the window

On the desktop, the in-process server hands native notifications straight to the shell, without going through any window, so a flag cannot ride on the notification. Each local window instead reports which notification kinds it plays an OpenChamber sound for (`nativeNotifications.ts`), and the shell shows those notifications with `silent: true`. The report ignores quiet hours and "play when" on purpose: one setting, the event switch, decides which sound a kind uses. It counts a kind only while the engine is unlocked, since a locked engine drops its first sound and the notification would then be silent. It names the instance the window shows (`runtimeKey`), and the shell matches it to the instance a notification came from, a missing key meaning the local one, so a window on one instance never silences another's notifications. The shell keeps the report per window and forgets it when the window closes or commits another page, and the window reports no kinds when it unmounts or shows an instance other than the desktop's own, so a closed or remote window never silences a notification it cannot replace with a sound.

A window that shows another instance reports no kinds at all (`isDesktopLocalOriginActive` gates the report, like the other local-only desktop capabilities), which also clears what it reported before the switch. A host notification therefore keeps its OS sound next to the window's own sound there. The shell already matches by instance, so reporting under the host key instead would cover those too; that is a product choice left open.


### Why the first output announces a main session and not the start of its turn

OpenCode announces the real start of a turn (`session.execution.started`, the status the sync layer stamps `live`) before the model has said anything, and a turn can then wait on a queue or a slow provider. The sound is meant to say that the agent is answering, so a main session waits for its first delta or tool call. A subagent has no such wait to explain: it announces at once, once per session id. A turn that ends before any output forgets its wait, and a status the host reported (`source: 'host'`) never starts one, since the host's record says a turn was already running when the page loaded. A child whose parent the window has not seen yet counts as a main session, the same gap the turn end sounds have; a session created in the same flush as its start is found in the flush's pending `session.created` events, because no store and no global list holds it before the flush publishes.

The claim of a main session's start names the turn by the message the first output belongs to (`agent-start:<session>:<message>`), not by the session. The server gives the message its id, so every window names the turn alike, and a queued follow-up turn right after another has a message of its own. A claim by session with a short life silenced that follow-up.

### Why ticks follow tool transitions and an edit is an edit, write or patch

A tick needs the state before and after a change, which `message.tool.transition` gives and a full part snapshot (`message.part.updated`) does not say anything about: snapshots arrive after reloads and resyncs, and a tick for them would be a sound for history. The edit sound uses `isFileChangeTool` (edit, write, patch). The file tree classifier `toolListingChanges` exists to tell which folder listings changed and names nothing for `edit`, the most frequent change, so it would miss most edits. Both sounds sit behind `toolSoundsWanted` and the on-screen check, so a background session never costs more than a settings read per transition.

### Why dictation throws audio away and does not delay the microphone

The start sound plays before the microphone opens, and a fast device can open it within the sound's length. Waiting for the sound to finish would add its length to every dictation start. Instead `dictationStarted` resolves to the time the sound has left the speakers and the capture drops every audio block that reaches back to that time (`isBeforeCaptureStart`); a block is dropped whole, so the audio kept starts at most one block (about 85 ms) after the sound.

The engine computes that time, because only it knows what a fixed length gets wrong: the context may first have to resume (the sound then starts later), the device adds its output and base latency, and a custom file lasts as long as its stored length says. It adds 150 ms for the room. A sound that was not played (throttle, locked, no free voice, refused resume) resolves to 0 and the capture keeps everything. The capture does not wait for the answer: until it arrives, audio is thrown away for at most one second, which only matters when the context resumes or a custom file loads. In the usual case the answer settles long before the microphone opens.

The hold that keeps other sounds back is taken right after the start sound and released after the microphone closed (confirm) or at once (cancel, which keeps nothing). Each dictation hook takes its own hold (`beginDictationCapture` returns the function that releases it), so the unmount of an idle hook or the end of one recording cannot release the hold of another that still records. A single shared boolean did that.

### Why only a continuous pull request push can play, and every record sets the baseline

A tracked record carries the server's clock in `fetchedAt`, and the window's clock can differ from it by minutes, so "newer than the moment the window started" cannot tell a live record from an old one. What tells them apart is how the record arrived and what the server says about it. The server answers what the window follows when it subscribes and after every reconnect (the state of the moment, not news), and it pushes a change when it sees one. A push is not always news either: after a server restart the restored entries are read at once, a window that was hidden refreshes when it returns, and a read that follows a failed one sees whatever moved meanwhile, and each of those pushes the difference. So the server marks a pushed record `continuous` only when its previous read succeeded, knew the item, and was within the item's cadence plus 30 seconds of this one (`tracked-items/DOCUMENTATION.md`). `interest.ts` hands the store the `source` of each batch, and the store tells `subscribeTrackedRecordsReceived` listeners the source and the `continuous` mark of each record, with what it held for the item before and after. The watcher sets the baseline of an item from every record, also from one the store skips as equal to the one it holds, and compares only records that are both pushed and continuous. A record restored from storage is the baseline when no record came before it. A server that sends no mark (an older host) therefore plays no pull request sound.

Two earlier shapes failed. Diffing the store's records could not tell an answer after a remount or reconnect from a push, so a merge that happened while the connection was down played when the answer arrived. And the store skips an answer equal to the restored record, so the first push after a reload became the baseline and its change never played. A third trusted every push, so a pull request merged overnight played "merged" on launch, when the server's first refresh pushed it. A reload, a reconnect and a server catch-up now play nothing for what changed meanwhile; a continuous push after them is compared with what they left. Baselines are kept while the sounds are off, so switching one on never compares against a state from long ago. A merge plays only the merged sound, not the checks sound that came with it. Claims name the request, the kind and the head commit, with a 30 second life: a re-run of the same commit's checks still plays.

### Why a lost connection needs 4 seconds and a visible window

A WebSocket that drops and recovers within a few seconds is routine on a laptop or a phone, and a sound for each would be noise. Only a connection that worked (`connected` to `reconnecting`) can be lost, so the first connect and an instance switch never are. A window that drops its socket while hidden says nothing and owes no "restored" sound, so a phone returning from a pocket stays quiet. A phone's socket usually dies while the page sleeps and the page learns of it only once it runs again, when the window is already visible; a drop noticed within 10 seconds of the window being shown again counts as hidden too. `watch` follows `visibilitychange` for that and is stopped with the other sources. "Hidden at any time since the last connected" was the first idea and was dropped: every window that was ever switched away from would then stay silent about a real outage until its next connect. Electron windows keep `visibilityState` visible while unfocused, so they do announce. "Restored" is owed only when the settings allowed the "lost" sound (`connectionLost` returns that), so a lost sound that was off, muted or held by "in background" is not followed by a restored one. The claim lets the windows of one origin, which lose the server together, play one sound.

### Why terminal and command sounds are named by process

A terminal tab and the same server session exist in every window, with different tab ids. The claim names the server session and the sequence of its `exit` event (`terminal-done:<id>:<sequence>`, 30 seconds), so two windows play one sound, and a window set to "in background" that looks at the app keeps the claim without a sound. A background command has an id of its own and ends once (`terminal-done:shell:<id>`, 10 minutes).

The sequence is in the key because a terminal tab's session id is the tab id: a restart keeps it, and a shell re-created after it exited reuses it. A claim by id alone (10 minutes, the first design) silenced the real end of the next process of the same tab. A stream that delivers an exit without a sequence announces nothing, since the end could not be told from another.

A terminal's end is announced from the live `exit` event of its stream, in `TerminalView` and in the project action runner, before a close-on-exit removes the tab, and from the server's session-change notice that names the exited session and its exit sequence (`workspaceSources.ts`). The first design diffed the terminal store for a tab going from `running` to `exited`, and that also fires for a fatal stream error, for the list read after a server restart, for a late snapshot that says exited, and for a stop made in another window, while it misses a tab that close-on-exit removed. The store records what the UI believes; the `exit` event is what the process did.

### Why the server names an exited session in its session-change notice

The stream handlers only run where a view or the action runner streams that session, and the runner follows the project the window shows. An action that ended in another project played nothing. The alternative was one window-wide subscription to the stream of every running action tab, which still misses a run another window started and a plain shell in a project the window does not show. The notice already goes to every client on each session end, so it carries the session id and the sequence of its exit event, and one subscriber in `workspaceSources.ts` announces it. The stream handlers stay: VS Code has no event stream, and a window whose control stream is down still hears its terminal's own. Both paths build the same claim, so one end plays once.

### Why a stop is a short claim of the session and not a claim of the end

A stop the user makes in the project action runner calls `terminalStopped`, which takes `terminal-stopped:<id>` silently for 30 seconds before the process dies; `terminalFinished` plays nothing in any window of the origin while it holds. The stop cannot claim the end itself, because the exit sequence is unknown until the exit arrives. Ctrl+C, then a forced kill after a second, fit well inside 30 seconds, and an action run gets a session id of its own, so the claim covers only that run. When the stop fails and the action goes back to running, `terminalStopFailed` releases the claim, so the process's real end still plays. Closing a tab and restarting a shell take no claim: closing retires the server session and a restart drops the old process's events, so neither sends an exit. A command the user stopped, one whose end fell into a stream gap, and one the turn waited for are not announced either.

### Why commits are announced from the git HTTP adapter

Four call sites create commits (the changes panel twice, the mobile surface, the dirty-branch switch), and all go through `gitApiHttp.createGitCommit`, the same adapter that announces pushes. One announcement there covers them, and a fifth caller needs no change. The bus (`gitCommitEvents.ts`) uses the push scope, so a commit that ran against another runtime than the window's is ignored. VS Code has no source control panel, so the commit and push rows are hidden there.
